# План реализации MVP: датчик и приложение для ухода за растениями

> Документ собран на основе обсуждения. Используется как референс при работе с Claude Code — план в контексте сильно снижает галлюцинации модели и держит её в рамках проектных решений.

---

## 1. Концепция продукта

Беспроводной датчик в горшке + PWA-приложение для новичков, которые завели растение и не знают, как за ним ухаживать. Главная цель — не убить растение пользователя из-за нехватки знаний или времени.

**Ключевые принципы:**

- Уведомления — это действия, а не алерты. Не «низкая влажность», а «полей 150–200 мл тёплой отстоянной воды».
- Главный экран отвечает на вопрос «всё ли в порядке?» за секунду. Светофор, не графики.
- Минимум фрикции в онбординге: первая ценность (зелёный/красный статус + одно конкретное действие) — сразу.
- Никакой геймификации, бейджей, социальной ленты, общих советов «ИИ-помощника» — это маркетинговый шум, а не польза.

## 2. Целевая аудитория и платформа

- Абсолютные новички в уходе за растениями.
- Россия и СНГ. Только русский язык на MVP.
- **PWA**, без публикации в App Store / Google Play. Установка «добавить на главный экран» из браузера.
- Telegram-бот не используется (заблокирован в РФ).

## 3. Зафиксированные технические решения

### 3.1 Железо

| Компонент | Назначение |
|-----------|------------|
| ESP32-C3 SIMPLE ROBOT / Super Mini (4 МБ flash) | Главный контроллер, Wi-Fi |
| BME280 (I2C) | Температура, влажность воздуха, давление |
| GY-30 (BH1750, I2C) | Освещённость в люксах |
| Ёмкостный V1.2 (ADC) | Влажность почвы |
| Li-Po 3.7V 450 mAh | Питание |
| TP4056 | Зарядка через USB |
| Boost-преобразователь | Повышение напряжения батареи до питания платы |
| Корпус с бытовой герметичностью | Защита от случайных капель, не для полива на сам датчик |

**Распиновка ESP32-C3 (Super Mini):**

| GPIO | Функция | Что подключено |
|------|---------|----------------|
| GPIO8 | I2C SDA | BME280 + BH1750 (общая шина) |
| GPIO9 | I2C SCL | BME280 + BH1750 (общая шина) |
| GPIO4 (A4) | ADC | Датчик влажности почвы V1.2 (AOUT) |
| GPIO10 | GPIO | Кнопка сброса |
| GPIO20 / GPIO21 | UART | Отладка по USB (не использовать в проде) |
| GPIO0, 1, 2, 3, 5 | резерв | Свободны для будущего |

**Известные ограничения и риски:**

- TP4056 по умолчанию заряжает током 1 А — для аккумулятора 450 mAh избыточно (рекомендуется ~225 мА). Заменить токозадающий резистор для увеличения срока службы аккумулятора.
- Нет датчика температуры почвы и EC (солевой состав) — приложение не сможет говорить о подкормке на основе данных, только по таймеру.
- Ёмкостный V1.2 не откалиброван заводом — обязательна процедура калибровки при первой установке.
- **Контроль заряда — программный, без аппаратного делителя напряжения.** Оценка по времени работы с момента последней зарядки. Подробнее в разделе 3.2.
- **Риск Wi-Fi антенны:** у штатной чип-антенны ESP32-C3 Super Mini известна слабая дальность через стены. Обязательно проверить в Фазе 0 на типичной топологии квартиры. Если плохо — рассмотреть версию с u.FL разъёмом и внешней антенной.
- **Риск тока покоя преобразователя:** дешёвые boost-преобразователи (MT3608, SX1308, FP6291) могут есть 0.5–2 мА даже когда ESP32 в deep sleep. Это убивает автономность независимо от оптимизаций прошивки. Обязательно измерить реальный ток покоя в Фазе 0 (мультиметром, в разрыв батарея↔преобразователь). Если >200 мкА — пересмотреть схему питания (например, питать ESP32 напрямую через LDO без повышения).

### 3.2 Прошивка

- **Framework:** ESP-IDF (не Arduino).
- **Связь с сервером:** Wi-Fi, HTTPS, POST батчем.
- **Замеры:** каждые 10 минут.
- **Буфер:** кольцевой в RTC RAM (~8 КБ, хватает на ~3 суток замеров).
- **Отправка:** раз в час пачкой (6 замеров).
- **Внеплановая отправка:** при выходе значений за критичные пороги.
- **Fallback:** при долгом отсутствии связи — сброс буфера в LittleFS.
- **Аутентификация датчика:** device_token, не email/пароль пользователя.
- **Первичная настройка Wi-Fi:** SoftAP + captive portal на 192.168.4.1.
- **Сброс датчика:** длительное нажатие физической кнопки → стирание NVS → возврат в SoftAP.
- **OTA-обновления:** через HTTPS с бэкенда. Заложить с самого начала.

**Программный контроль заряда (без пайки делителя):**

- В NVS хранится `last_full_charge_timestamp` (время последней отметки «заряжен»).
- В NVS хранится `cycles_since_charge` (счётчик циклов просыпания/замера/отправки с момента зарядки).
- Эти два поля передаются на сервер вместе с каждым батчем.
- При нажатии кнопки «я зарядил» в приложении бэкенд отправляет команду датчику при следующем подключении → обнуление счётчиков.
- Сервер считает оценочный процент по формуле: `100% × (1 − cycles_since_charge / cycles_per_full_battery)`, где `cycles_per_full_battery` калибруется по реальному циклу разрядки конкретного датчика (изначально берётся теоретическая оценка ~50 дней).

**Ожидаемая автономность:** 1.5–2 месяца при адаптивных замерах (ночью реже). **Будет переоценено** после измерения тока покоя преобразователя в Фазе 0 — если преобразователь жадный, реальная автономность может оказаться 2 недели вместо 2 месяцев.

### 3.3 Бэкенд

- **Стек:** Node.js + TypeScript + Fastify + Prisma + PostgreSQL.
- **Хостинг:** Railway / Render / Fly.io (бэкенд), Neon / managed PG (БД).
- **Аутентификация пользователей:** magic link на email (Resend / Postmark).
- **Пуш-уведомления:** Web Push API + VAPID + библиотека `web-push`.
- **Plant.id API:** прокси на бэкенде, ключ не светится во фронте.
- **Контроль заряда:** оценочный процент считается на сервере из `cycles_since_charge` + калиброванный `cycles_per_full_battery` для каждого устройства. Поле `battery_estimate` ∈ {full, medium, low, critical}. Самообучение: после каждого полного цикла «отметка заряжен → следующая отметка заряжен» уточняется реальное значение `cycles_per_full_battery` для конкретного устройства.
- **Мониторинг:** Sentry (free tier) для ошибок, uptime-мониторинг.
- **Аналитика:** Plausible / Umami / Posthog free tier.

### 3.4 Фронтенд

- **Стек:** React + Vite + TypeScript + Tailwind CSS + shadcn/ui.
- **PWA:** vite-plugin-pwa, Service Worker, manifest, иконки, splash screens.
- **Хостинг:** Vercel / Cloudflare Pages.
- **Индикатор заряда:** иконка батареи в карточке датчика (4 состояния: full / medium / low / critical). Никаких конкретных процентов — только качественная оценка + ориентировочный остаток в днях после калибровки. Явное упоминание «оценка по расходу» в подсказке. Кнопка «я зарядил датчик» рядом.

### 3.5 Идентификация растений

- **Сервис:** Plant.id (Kindwise) only. PlantNet и гибрид — постMVP.
- **Лимит:** 3 запроса/неделю на пользователя, rolling 7 дней.
- **Защита от обхода:** привязка к датчику + magic link email-подтверждение.
- **Порог уверенности:** 80% (точное значение — после тестов).
  - ≥80% — применяем автоматически.
  - <80% — показываем топ-3 с фото из ответа Plant.id, пользователь выбирает.
  - «Ничего не подходит» — ручной выбор из курируемой базы (бесплатно) или новая попытка (минус кредит).
- **Запрос = 1 кредит** независимо от количества прикреплённых фото (Plant.id принимает 1–3 фото за раз).
- **Ответ Plant.id не хранится для повторного выбора.** Re-identification = новый запрос из лимита.
- При исчерпании лимита: показать «попробуй через неделю» или ручной выбор из базы.
- **Сброс датчика не сбрасывает лимит** — он привязан к аккаунту.

### 3.6 База знаний о растениях

- **Курируемая база топ-50 видов** — ручное наполнение из RHS, Missouri Botanical Garden, IFAS (University of Florida). Кросс-проверка трёх независимых источников.
- **Поля на вид:** диапазоны влажности почвы для полива, освещённости (мин/опт/макс в люксах), температуры, влажности воздуха, конкретные инструкции по поливу (объём, частота, тип воды).
- **Fallback:** Perenual API для остальных видов с пометкой «общие рекомендации, могут быть неточны».
- **Архитектурно заложить:** таблица `overrides` (user_id + plant_species_id) для будущего краудсорсинга.

## 4. Скоуп MVP: «Полезный MVP»

### Входит:

- Несколько растений на аккаунт (несколько датчиков, связь 1 датчик = 1 растение).
- Полный онбординг: подключение датчика → идентификация по фото → калибровка → привязка профиля.
- **Подбор места:** «походи с датчиком по комнате», карта «хорошо/нормально/плохо» для конкретного вида.
- Главный экран со светофором, текущими показаниями всех сенсоров.
- Кнопка «я полил» (ручная отметка действий ухода).
- Уведомления-действия с конкретикой (объём, тип воды, шаги).
- Защита от перелива: если почва влажная — гасим уведомление о поливе по таймеру.
- Карточка растения: вид (можно изменить), требования, графики за 7/30 дней.
- Метки событий ухода на графиках (полив, подкормка, пересадка).
- Журнал ухода: лента событий по растению, ручное добавление задним числом.
- **Индикатор заряда датчика + уведомление о низком заряде + кнопка «я зарядил».**

### Не входит (постMVP):

- Диагностика проблем по фото симптомов.
- Обучающие сводки и аналитика («ваш фикус потребляет столько воды раз в N дней»).
- DLI (интегральная оценка света за день).
- Краудсорсинг overrides из реального использования.
- Платная подписка.
- Поддержка экзотических видов с глубокими данными.
- Интеграция с умным домом.
- Мультиязычность.
- Точный аппаратный контроль заряда (делитель напряжения или fuel gauge MAX17048).

## 5. План по фазам

**Темп оценок:** ~20 часов/неделю, Claude Code делает черновую работу. Реалистичный пессимистичный сценарий — растяжение в 1.5–2 раза.

### Фаза 0 — Подготовка (неделя 1)

- [ ] Курирование базы топ-50 растений вручную (JSON/YAML).
- [ ] Регистрация на Plant.id, получение ключа, тест на 5–10 фото своих растений.
- [ ] Регистрация доменов (PWA и API субдомены).
- [ ] VAPID-ключи для Web Push.
- [ ] Аккаунты на Resend, Railway/Render, Sentry.
- [ ] Wireframes 6 ключевых экранов (Figma или эквивалент).
- [ ] **Проверка Wi-Fi антенны** на типичной топологии (датчик у окна, роутер в другой комнате через 1–2 стены). Если плохо — заказать версию с внешней антенной или предусмотреть в корпусе место под u.FL.
- [ ] **Измерение тока покоя преобразователя** мультиметром в разрыв между батареей и преобразователем при ESP32 в deep sleep. Если >200 мкА — решить, что делать со схемой питания до Фазы 2.

**Выход:** база растений, ключи и аккаунты, макеты, понимание реальной автономности и качества связи.

### Фаза 1 — Бэкенд-каркас (недели 2–3)

- [ ] Скелет Node.js + Fastify + TS + Prisma.
- [ ] Схема БД: users, devices, plants, plant_species, measurements, care_log, notifications, push_subscriptions, overrides, **device_charges** (для самообучения cycles_per_full_battery).
- [ ] Эндпоинты для датчика (регистрация, приём батча, device_token аутентификация, **получение команды «зарядили — обнули счётчики»**).
- [ ] Эндпоинты для фронта (magic link, привязка датчика, CRUD растений, чтение измерений, журнал, **отметка «я зарядил датчик»**).
- [ ] Прокси к Plant.id с учётом лимитов rolling 7 дней.
- [ ] Импорт курируемой базы + Perenual fallback.
- [ ] Логика расчёта оценочного заряда (`battery_estimate` из `cycles_since_charge`).
- [ ] Деплой на Railway/Render, HTTPS.
- [ ] Базовый rate limiting.

**Выход:** работающий API, проверяемый через curl/Postman.

### Фаза 2 — Прошивка датчика (недели 4–5)

- [ ] Базовый проект ESP-IDF, partition table.
- [ ] Инициализация BME280, BH1750, V1.2 (ADC) по распиновке из раздела 3.1.
- [ ] Калибровка V1.2 (две точки в NVS).
- [ ] Цикл deep sleep + замер + RTC RAM.
- [ ] Wi-Fi отправка батча каждые 6 замеров.
- [ ] **Счётчик `cycles_since_charge` в NVS, отправка с каждым батчем. Приём команды «обнули счётчик» от сервера.**
- [ ] Captive portal на SoftAP с формой настройки + код привязки.
- [ ] Логика критичных событий (внеплановая отправка).

- [ ] Fallback в LittleFS при долгом оффлайне.

### Фаза 4 — Уведомления и действия (неделя 8)

- [ ] Правила: полив, температура, освещённость.
- [ ] **Правило: низкий заряд датчика (за неделю до расчётного исчерпания).**
- [ ] Защита от перелива (проверка реальной влажности почвы).
- [ ] Генерация текстов уведомлений с конкретикой (объёмы из карточки вида).
- [ ] Web Push: подписка на фронте, отправка с бэкенда, диплинки в карточку растения.
- [ ] Кнопка «я полил» с записью в care_log + сброс таймера.

**Выход:** уведомления приходят, ведут в нужный экран, пользователь отмечает действия.

### Фаза 5 — Карточка растения и история (неделя 9)

- [ ] Карточка растения: фото, вид, требования, текущий статус.
- [ ] Графики за 7/30 дней по 4 параметрам.
- [ ] Метки care_events на графиках.
- [ ] Ручное добавление событий задним числом.
- [ ] Журнал ухода: лента, редактирование, удаление.
- [ ] Список растений на главной, переключение, смена выбранного.
- [ ] Изменение вида растения (новая идентификация или ручной выбор).
- [ ] **Оценка остатка дней заряда после первого полного цикла зарядки.**

**Выход:** пользователь ведёт несколько растений, видит историю.

### Фаза 6 — Шлифовка и реальный тест (неделя 10)

- [ ] 5 прохождений полного пути разными людьми, фиксация проблем.

- [ ] Аналитика: счётчики ключевых событий.
- [ ] Бэкапы БД, мониторинг uptime, Sentry.

**Выход:** продукт, готовый к показу реальным пользователям.

## 6. Итоговая оценка

- **Оптимистично:** 10 недель = ~2.5 месяца.
- **Реалистично-пессимистично:** 4 месяца.
- **Главные риски срыва сроков:** железо (корпус, герметичность, ток покоя преобразователя, Wi-Fi антенна), курирование базы (легко растянуть в исследование), Claude Code на нетиповых задачах требует переделок.

## 7. Открытые вопросы / решения на потом

- Точное значение порога уверенности Plant.id (80% — стартовая гипотеза, корректируется по данным).
- Адаптивная частота замеров (ночью реже) — решение во время Фазы 2.
- Платная разблокировка дополнительных идентификаций (Stripe / ЮKassa) — постMVP.
- Мерчандайзинг датчика (QR на коробке, инструкция) — нужен к моменту первых продаж/раздач.
- Бизнес-модель: продажа железа, подписка, и то и другое.
- Точный аппаратный контроль заряда (делитель напряжения или MAX17048) — если в реальном использовании оценочный заряд часто врёт и пользователи теряют данные, переходим на пайку делителя.
- Решение по преобразователю питания по результатам измерений в Фазе 0.

## 8. Что использовать как контекст для Claude Code

При работе с Claude Code всегда прикладывать к промпту:

1. Этот документ полностью (или релевантный раздел).
2. Схему БД (после Фазы 1 — экспорт из Prisma).
3. Контракты API (после Фазы 1 — OpenAPI/JSDoc).
4. Дизайн-токены и компоненты shadcn/ui которые уже использованы.

Без контекста Claude Code часто принимает решения, противоречащие зафиксированным в этом документе (например, добавляет ненужную сложность, выбирает другую библиотеку, ломает паттерны). Поддерживать этот документ актуальным по мере работы — обязательно.
